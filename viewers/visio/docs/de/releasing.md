# Veröffentlichung

Die Visio-Pakete werden durch den eigenen Ablauf des `ooxml`-Repositorys veröffentlicht, der in dessen `docs/releasing.md` beschrieben ist: Das Skript `scripts/release-plan.mjs` im Stamm versioniert jedes Paket anhand der konventionellen Commits seit dem letzten Tag `<npm-name>@<version>`, und die Workflow-Datei `.github/workflows/release.yml` im Stamm setzt Tags, schreibt Changelogs und veröffentlicht über npm-Trusted-Publishing (OIDC und Provenienz, ohne Token). Die Paketliste für Visio ist `viewer('visio', ...)` im Skript `scripts/viewer-packages.mjs` des Stamms (`viewers/visio/scripts/viewer-packages.mjs` ist eine Sicht darauf für die Build-Skripte). Der Ordner `.github/` dieses Viewers ist wirkungslos.

Acht Pakete werden ausgeliefert: `visio-core` und `visio-{react,vue,angular,svelte,solid,vanilla}-viewer` aus `packages/{core,react,vue,angular,svelte,solid,vanilla}` sowie `visio-viewer-mcp` aus `mcp`. Eine Änderung in `src/` oder `packages/bindings/src/` dieses Viewers, in `scripts/build-packages.mjs` oder in `tsconfig.build.json` veröffentlicht alle sechs Viewer-Pakete; eine Änderung im eigenen Verzeichnis eines Pakets veröffentlicht nur dieses Paket. Die Viewer-Implementierung selbst ist `ooxml-ui/visio` (`src/ui/src/visio`) und wird mit `ooxml-ui` veröffentlicht. Die Pakete hängen von `ooxml-core` und `ooxml-ui` über einen Workspace-Bereich ab; der Ablauf der Veröffentlichung schreibt jeden in einen Caret-Bereich auf die Version um, die mit ihm veröffentlicht wurde. Reine Änderungen an Dokumentation und Tests veröffentlichen keine Pakete, sofern sie nicht die README eines ausgelieferten Pakets ändern.

`bun run check` in `viewers/visio` prüft Quellcode, Adapter, Dokumentation, Builds und die gepackten Verbraucher gegen den Kern und die Oberfläche der Registry (`bun run test:packages`). CI führt die gepackten Verbraucher mit `--workspace-runtime` aus (`bun run test:packages:workspace`). Dabei werden `ooxml-core` und `ooxml-ui` aus diesem Checkout gepackt, so wie eine Veröffentlichung sie gemeinsam ausliefert. `bun run test:browser` prüft das Verhalten im Browser und endet mit derselben Prüfung gepackter Pakete in einem Browser (`test-packages-browser.mjs --workspace-runtime`). Der Build enthält beide Browser-Worker, erzeugt TypeScript-Deklarationen und stellt den nativen Svelte-Quellcode sowie die Server-Einstiegspunkte für Solid und Svelte bereit.

Veröffentlichen Sie niemals von Hand mit `npm publish` und schieben Sie niemals Release-Tags von Hand. Eine fehlgeschlagene Veröffentlichung wird über die Eingabe `tag` des Release-Workflows erneut ausgeführt; dabei werden Versionen übersprungen, die bereits auf npm liegen.

Die Herkunft der Release-Werkzeuge ist in `scripts/RELEASE-PROVENANCE.md` festgehalten.
