## Added

- `ooxml-core/visio`, `visio-core` and Visio viewers: Visio drawings open with pages of up to about 10,000 shapes as Visio saves them. The default XML limits are now 1,500,000 nodes per part and 2,000,000 per package. The ten-second load deadline is unchanged.
- `ooxml-core/visio` and `visio-core`: package limits gain `maxXmlHeapBytes` and `maxXmlHeapPerInputByte` (4,096), which bound the memory one read or edit may take. By default `maxXmlHeapBytes` follows the host's heap. It is the heap limit Node reports (`v8.getHeapStatistics().heap_size_limit`) or a Chromium page reports (`performance.memory.jsHeapSizeLimit`), less 256 MiB, divided by 1.6. That is 280 MiB under Node's `--max-old-space-size=512`, 440 MiB under 768, 600 MiB under 1024 and about 2.5 GiB under Node's usual 4 GiB default. Where the runtime reports no limit (Firefox, Safari, web workers, Bun) it is 480 MiB. Set it lower when the same heap holds other large data or runs several reads at once.
- `ooxml-core/visio`, `visio-core` and Visio viewers: `parseVsdx` reports `edit-size-limit` first among its diagnostics when the drawing is too large to edit here. That is when its pages hold more than 100,000 ShapeSheet cells, or when an edit of it would not fit `maxXmlHeapBytes`. The Visio viewer then opens the drawing read-only and says why in its language.
- `ooxml-ui/pptx`: the scroll window every binding's thumbnail rail uses is exported: `createVirtualWindow`, `createDeferredRows`, `sameRenderedWindow`, `railHasFocus`, `focusCurrentRow` and their constants.

## Changed

- `ooxml-ui` and Visio viewers: the Visio viewer's `zoom-change` event fires once per zoom gesture instead of once per wheel step, when the zoom is applied. That is 300 ms after the last input, when the gesture ends, or before a pointer press or scroll. Until then the `zoom` property still reads the zoom the gesture started from.
- `ooxml-ui` and Word viewers: Word's SmartArt Design colour and style galleries load the built-in SmartArt definitions (about 390 KB compressed) when a SmartArt is selected, not when the editor opens.

## Fixed

- `ooxml-core`, `ooxml-ui` and Visio viewers: a Visio drawing that is too large to open says how many shapes its page has, in the viewer's language.
- `ooxml-ui` and Visio viewers: the Visio viewer shows a refused edit ("Edit rejected: ...") in its language. An edit refused because the drawing has too many ShapeSheet cells now says so: "This drawing is too large to edit: an edit follows at most 100000 ShapeSheet cells."
- `ooxml-ui`: `office-ui-tab-strip` no longer scrolls to its selected tab on updates that change neither the selection nor the tabs.
- PowerPoint viewers: paging through slides with the keyboard while the thumbnail rail has focus keeps focus on the current slide's thumbnail, as PowerPoint does. Before, focus was lost once the first thumbnail scrolled out of the rail, and in the Vue, Svelte and vanilla viewers the keys then scrolled the rail instead of changing the slide.
- PowerPoint viewers: undoing or redoing a New Slide while the thumbnail rail has focus keeps focus on the current thumbnail, so Ctrl+Y and the other shortcuts keep working. The vanilla viewer also keeps it when the rail is redrawn.
- Visio viewers: pressing a selection or rotation handle while a zoom is still previewing starts the drag, and the rotation handle moves with the previewed drawing.

## Security

- `ooxml-core/visio`, `visio-core`, `visio-viewer-mcp` and Visio viewers: no Visio file can exhaust the heap of the host that reads or edits it. A read or an edit now has one memory budget for every package it opens and the model it builds. The budget is estimated before each XML part is parsed and sized from the host's heap. A drawing that does not fit is refused with the code `LIMIT_XML_MEMORY` and a message, in the viewer's language, saying how much memory it would need. Past 64 MiB a read may take at most 4,096 bytes of memory for each byte of its file, so a small file of dense XML is refused in well under a second. Measured in Node 24 under 512, 768 and 1024 MiB heaps (255 runs over 29 files, reads and edits), every file opened or was refused, and peaks stayed at or below 503, 648 and 902 MB. Before, a 411 KB file reached 856 to 907 MB and ended a 512 or 768 MiB Node process, and an edit reached 1.4 to 2.5 GB. A page of 10,000 rectangles saved by Visio needs a heap limit of about 1,000 MiB (Node's `--max-old-space-size=820`, where it peaks at 650 to 710 MB) and opens in the viewer's parsing worker.

## Performance

- PowerPoint viewers: the slide thumbnail rail reads scrolling once per frame and keeps the thumbnails that stay in view. In a deck of 50 or more slides, thumbnails that scroll into view are drawn once scrolling pauses, one per frame, so the rail scrolls at full frame rate. Moving to another slide no longer redraws the visible thumbnails.
- `pptx-react-viewer` and `@christophervr/pptx-viewer`: moving to another slide no longer copies and compares the whole deck for the undo history.
- `ooxml-ui` and Visio viewers: zooming a Visio drawing with Ctrl+wheel, a pinch, the zoom slider or the + and - keys scales the drawing smoothly and renders the page once when you stop. The end zoom and scroll position are unchanged.
- Office suite: the home and product landing pages no longer download the Teams engine or the package tools, so they load about 54 KB of compressed JavaScript instead of about 500 KB.
- Office suite: creating a new Word, Excel or Visio file no longer downloads the automation bundle (about 860 KB compressed).
- Office suite: the styles arrive as one content-hashed stylesheet instead of a chain of thirteen, so the first screen paints sooner.

## Accessibility

- PowerPoint viewers: when the thumbnail rail shows only the rows in view (a deck of 50 or more slides without sections), each row gives its position and the slide count (`aria-posinset`, `aria-setsize`), so screen readers announce where it sits in the deck.
